LRN CPU Monitor - NEW Windows Service - 2026-09-11
==================================================
This is a NEW standalone service. It is NOT an overlay.
It does not touch the Website, the Report Worker, or any database.
No SQL to run. No IIS change. No app_offline needed.

What it does
------------
Watches every process. When one stays above the CPU threshold for
several consecutive samples it logs the application name, full path,
PID, owner, session, command line and the parent process that
launched it. For sqlservr.exe it also asks SQL Server which client
app and query is burning the CPU.


INSTALL (elevated PowerShell on the VM)
---------------------------------------
  1. Unzip the whole package to a temp folder on the VM.
     Keep Install-CpuMonitor.ps1 next to the CpuMonitor folder.

  2. Run PowerShell AS ADMINISTRATOR, then:

       cd <unzipped folder>
       .\Install-CpuMonitor.ps1

     Default install path: D:\LRN\Release\CpuMonitor
     To change it:  .\Install-CpuMonitor.ps1 -InstallPath "E:\LRN\CpuMonitor"

  3. The script is safe to re-run. On an upgrade it stops the service,
     replaces binaries, KEEPS your existing appsettings.json (old copy
     saved as appsettings.json.previous) and restarts.

Requires the .NET 8 runtime on the VM. The script checks and stops
with a clear message if it is missing.


SERVICE ACCOUNT - IMPORTANT
---------------------------
The script creates the service as LocalSystem. Leave it that way.

Measured on 411 processes as a normal (non-admin) user:
  - CPU usage    : readable for ALL 411 processes
  - Path/cmdline : readable for only 156 of 411 (38%)

So a non-LocalSystem account still DETECTS high CPU from any user
including admins, but the path and command line come back
"(unavailable)" for about 60% of processes, which defeats the log.

Verify after install:
  sc.exe qc "LRN - CPU Monitor"
  SERVICE_START_NAME must read LocalSystem


CONFIGURE BEFORE YOU RELY ON IT
-------------------------------
Edit  <InstallPath>\appsettings.json  then restart the service.
Settings reload live, but a restart is the sure thing.

  CpuThresholdPercent      90     breach threshold
  NormalizeByCoreCount     true   see the warning below
  SampleWindowSeconds      5      measurement window
  PollIntervalSeconds      10     gap between windows
  ConsecutiveSamplesBeforeAlert  3   windows before it alerts
  AlertCooldownMinutes     15     repeat suppression per PID
  SqlConnectionString      ""     blank = SQL attribution OFF

THRESHOLD WARNING - read this before setting 90
  With NormalizeByCoreCount = true, 100% means EVERY core is busy,
  exactly like the Task Manager CPU column. On an 8-core VM one
  runaway single-threaded process only reads about 12%, so it will
  NEVER trip a 90% threshold.

  Pick one:
    a) Catch a consumed server   -> leave true,  threshold 90
    b) Catch one runaway thread  -> set false,   threshold 90
    c) Keep true and lower the threshold to about 90 / core count

To turn on SQL attribution, set SqlConnectionString and grant the
login VIEW SERVER STATE. Prefer Integrated Security so no password
sits in the config file:

  "SqlConnectionString": "Server=<host>;Database=master;Integrated Security=True;TrustServerCertificate=True"

Also worth doing separately: set "Application Name=" in each of our
services' connection strings. Without it every caller shows up as
".Net SqlClient Data Provider" and the SQL attribution cannot name
which of our apps caused the load.


LOGS  (under <InstallPath>\Logs)
--------------------------------
  cpu-breaches-<date>.txt   BREACHES ONLY          kept 180 days
  cpu-monitor-<date>.txt    everything             kept 30 days
  cpu-breaches.jsonl        one JSON per breach    kept until removed

Watch it live:
  Get-Content "D:\LRN\Release\CpuMonitor\Logs\cpu-breaches-*.txt" -Wait -Tail 20


ROLLBACK
--------
  .\Uninstall-CpuMonitor.ps1                 removes service, keeps logs
  .\Uninstall-CpuMonitor.ps1 -RemoveFiles    removes everything

Nothing else is affected. Removing this service cannot impact the
Website, the Report Worker, or any database.
