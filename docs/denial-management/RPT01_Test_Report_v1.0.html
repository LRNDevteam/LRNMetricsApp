Section 02

What the RPT-01 cases prove

23 test methods, 49 cases after theory expansion, in two files. Grouped by the claim each group makes.

16

The generated SQL is well-formed

ArActivityReportTests

Every combination of grain, Latest-Activity-Only, grouping and analyst scope is generated and parsed with the real T-SQL parser — not a regex, not a string check. Run twice over two schemas: a fully migrated lab, and one where every optional column is absent.

That second pass is the one that matters operationally. The repository applies its migration per lab on first use, so a lab that has not yet been touched is missing the new columns, and the report has to degrade rather than throw.

  • GeneratedSql_Parses_OnAFullyMigratedLab — 8 cases
  • GeneratedSql_Parses_WhenEveryOptionalColumnIsMissing — 8 cases
  • grains: Claim, Line · groupBy: none, analyst, action, payer, classification, activityType
2

The two counting decisions hold

the arithmetic that gets audited

These are the assertions the spec's business rules turn on, and both are places where an obvious implementation is wrong.

Escalation history rows are excluded from the spine. Raising one escalation writes one escalation row plus one history row per affected task, so counting history rows would inflate "escalations raised" on every multi-line claim. The escalation record is also the only place the reason, recipient and EscalationId live.

Balance is aggregated once per claim/analyst/day. Summing a balance snapshot per note event would multiply the same money by the number of notes — the spec calls this out explicitly and it is the single most likely way this report would overstate.

  • GeneratedSql_ExcludesEscalationHistoryRowsFromTheSpine
  • GeneratedSql_AggregatesBalanceOncePerClaimDay
9

Internal notes stay internal

role masking

Nine roles, each asserted for visibility. Client Manager, Account Manager and Lab User are masked; Admin, AR Manager, AR Reviewer and AR Analyst are not. Role strings are tested in both display and normalised form (Client Manager and client-manager, Lab User and labuser) so the punctuation-stripping match cannot regress.

Client-facing roles get masked notes, not missing rows — so a summary count still reconciles to the detail the user can see. Dropping the rows instead would make the summary disagree with the detail for exactly the audience least able to explain it.

11

Filter normalisation

before the query is built

Date-window handling, page-size clamping and the lab requirement. An inclusive end date becomes an exclusive upper bound; an inverted range is swapped rather than silently returning nothing; a window wider than a year is rejected; a lab is mandatory.

  • Normalize_TurnsAnInclusiveEndDateIntoAnExclusiveUpperBound
  • Normalize_SwapsAnInvertedRangeRatherThanReturningNothing
  • Normalize_RejectsAWindowWiderThanAYear · Normalize_RequiresALab
  • Normalize_KeepsAnExplicitTimeOnTheUpperBound
  • Normalize_DefaultsToTheLastSevenDaysOfActivity
  • Normalize_ClampsScreenPageSize — 4 cases (0→50, 10→25, 100→100, 5000→200)
  • Normalize_LetsAnExportTakeEveryFilteredRow
8

The workbook, and its reconciliation sheet

ArActivityReportExcelTests

The export is asserted against the spec's own worked example — three same-day notes on one claim by one analyst give 3 activity events and 1 claim-day worked, with balance $1,540 rather than $3,260. Critically, the assertion reads the workbook's Reconciliation sheet, which recomputes every measure from the detail rows rather than echoing the summary. A summary that agreed with itself but not with its detail would fail here.

Section 03

What these tests do not prove

This is the honest limit of a green run, and it should be read before anyone treats 320/320 as sign-off.

No test in this suite opens a database connection. They prove the SQL is well-formed and the arithmetic is right. They cannot prove that the columns the SQL reads contain anything. A nullable column that is null in every row of a real lab produces a report that renders perfectly and says nothing — and every one of these 320 tests would still pass.
  • Column population is untested. DenialTaskBoard.Task, DateOfService and ClaimUID in particular need checking on the chosen lab before sign-off.
  • Query performance is untested. The spec's NFR-001 asks for summary pages within 5 seconds. A three-way union over the event tables on a large lab is the obvious risk, and parse-checking says nothing about it. The new (LabId, event date) indexes on all three event tables — which had none — are the mitigation, but they are unmeasured.
  • The per-lab migration is untested against a real lab. The ALTERs are metadata-only and the script parses, but neither fact proves it applies cleanly over a lab's actual current schema.
  • Role masking is tested at the query layer only. That the UI also hides what it should is a separate check.
Section 04

Blocker: LRNLabDemo is not reachable

The acceptance test cannot run against LRNLabDemo today. This has nothing to do with RPT-01 — it is a lab-connection configuration gap that predates it.

LabConnectionResolver.Resolve() tries five sources in order. For LRNLabDemo, all five miss and it returns an empty string:

#Resolution stepResult for LRNLabDemo
1ConnectionStrings:Lab_{labId}not configured
2{LabConfigFolder}\LRNLabDemo.jsonfolder does not exist — configured as E:\LRN-Data\…, and this server has no E: drive. Dead for every lab.
3LRNMetricsLab.ConnectionKeyno matching vault secret
4known-name mapno LRNLABDEMO case
5fuzzy scan of ConnectionStringsno match among the 25 vault secrets

Two independent problems are visible here. The folder path is wrong for every lab — the real files sit at C:\LRN-Files\ApplicationFolder\CodingAutomation\Labs\, and each carries the DbConnectionString the resolver looks for. Labs 1–12 survive only because steps 3–5 rescue them. LRNLabDemo has no rescue: no file, no vault secret, no map entry.

Cheapest fix, no code change

  1. Create ConnectionStrings--LRNLabDemo in kv-lrnmetrics-prod, pointing at the LRNLabDemo database.
  2. Set ConnectionKey = 'LRNLabDemo' on the lab's LRNMaster.dbo.LRNMetricsLab row — step 3 then resolves it.
  3. Restart LRN.ReportsApi. Lab connections are resolved once at startup and cached, so a new lab needs a restart.
Fix the folder path separately, and deliberately. Pointing LabConfig:LabConfigFolder at the real directory changes how all thirteen labs resolve — step 2 would start winning over the vault. Three filenames also do not match their configured lab names (Augustus.json vs Augustus_Labs, PCRAL.json vs PCR_Dx_AL, PCRCO.json vs PCR_Dx_CO), so those three would keep falling through to the known-name map. Worth doing, but not in the same change as the acceptance test.
Section 05

Acceptance test

Run once the lab connection is fixed. This is the spec's own worked example, and it is the test that distinguishes a correct report from a well-formed one.

Pre-flight — is this lab's data usable?

Run first. If any of these is empty, the acceptance test will produce a clean-looking result that means nothing. 

-- Populated-ness of the columns RPT-01 renders. Anything near 0 is a problem.
SELECT
  COUNT_BIG(*)                                                       AS Tasks,
  SUM(CASE WHEN NULLIF(LTRIM(RTRIM([Task])),'') IS NOT NULL THEN 1 ELSE 0 END) AS HasTask,
  SUM(CASE WHEN DateOfService IS NOT NULL THEN 1 ELSE 0 END)          AS HasDOS,
  SUM(CASE WHEN NULLIF(LTRIM(RTRIM(ClaimUID)),'') IS NOT NULL THEN 1 ELSE 0 END) AS HasClaimUID,
  SUM(CASE WHEN AssignedOn    IS NOT NULL THEN 1 ELSE 0 END)          AS HasAssignedOn
FROM dbo.DenialTaskBoard WHERE LabId = @LabId;

-- Do the three event tables actually hold events for this lab?
SELECT 'History' AS Src, COUNT_BIG(*) AS Rows_ FROM dbo.DenialTaskHistory     WHERE LabId = @LabId
UNION ALL SELECT 'Notes',      COUNT_BIG(*) FROM dbo.DenialClaimNotes       WHERE LabId = @LabId AND IsDeleted = 0
UNION ALL SELECT 'Escalations',COUNT_BIG(*) FROM dbo.DenialClaimEscalations WHERE LabId = @LabId AND IsDeleted = 0;

The test

1

Pick one claim, one analyst, one day

Choose a claim in LRNLabDemo with a known insurance balance. Note the balance — you will assert on it.

2

Record five activities as that analyst, same day

Three notes, one status change, one escalation. Use the workflow app, not direct SQL — the point is to test the write path the reviewers use.

3

Run RPT-01 filtered to that claim and date

Expect 5 activity events and 1 distinct claim-day worked
4

Check the balance was not multiplied

Outstanding balance worked must equal the claim's balance once — not three times for the three notes.

Expect the claim balance, not 3× or 5× it
5

Check escalations raised is 1, not 5

On a multi-line claim, escalating writes one history row per affected task. If this reads higher than 1, the spine is counting history rows it should be excluding.

Expect escalations raised = 1 regardless of line count
6

Toggle Latest Activity Only

Expect exactly 1 row — the most recent qualifying activity
7

Export to Excel and read the Reconciliation sheet

It recomputes each measure from the detail rows. Every summary figure must match its recomputed counterpart, and the run id and generation metadata must be present.

Expect summary = recomputed, on every measure
8

Re-run as a Client Manager

Internal notes must be masked, not absent. The row count must be unchanged, so the summary still reconciles to the visible detail.

Expect same row count, masked note text
9

Confirm the balance-snapshot marking

Rows predating snapshot capture fall back to the current balance and are marked * / Current (not snapshot), and counted on the Summary sheet. On a demo lab most rows will be marked — that is correct, not a defect.

Expect pre-existing rows marked, new activity unmarked
