Section 01

The answer, first

No — we do not have all the data. We have most of it. The shortfall is concentrated in four specific places, and it follows one pattern: we record current state well and events poorly.

The four root causes

Nearly every gap below traces to one of these. Fix the four and eight of the nine reports become fully buildable.

  1. Completion is a flag, not an event. DenialTaskBoard.ActionCompleted is a bit and DateCompleted is a date, both overwritten in place. There is no completed-by, no timestamp, and no history. RPT-04 is built entirely on this, and RPT-02's completion measures and RPT-09's stop events depend on it too.
  2. Escalation responses are not linked to escalations. A response writes a DenialTaskHistory row with ActionType = 'ManagerEscalationResponse', carrying TaskID but no EscalationId. With one escalation per claim you can infer the pairing by timestamp; with re-escalation — which the spec explicitly requires reporting on — you cannot. RPT-07's whole Response and Rework column groups sit here.
  3. There are no point-in-time snapshots. DenialTaskBoard is mutated in place. Opening and closing workload (RPT-02) and the entire Movement group (RPT-06) need inventory as it stood on a past date. The spec anticipates this and says so: "current tables alone cannot reconstruct past inventory accurately."
  4. There is no manager or team dimension. AssignedTo is a free-text string. Seven of the nine reports list AR Manager or team as a required filter or column, and every one of them is a management report. This is the cheapest gap to close and the one that affects the most reports.
What this audit is. A static read of the DDL in LRN.ReportsApi/Sql/ and the SQL embedded in SqlDenialWorkflowRepository.cs. No lab database was queried — connection strings resolve from Key Vault and per-lab config on the application server, and those databases hold PHI. Before build, run the verification script in §4 against one real lab to confirm the columns are actually populated, not merely present. A nullable column that is null in every row fails a report just as hard as a missing one.

Do GAP-1 and GAP-2 first, regardless of report order. Between them they touch seven of the nine reports, neither changes a write path, and both are pure additions. Building any report before the bucket map exists means embedding status names in report SQL — exactly what the spec's configuration requirement prohibits, and exactly the thing that will need unpicking later.
Section 04

Build and test order

Nine reports, sequenced so each one reuses what the last one built and every one is testable on its own. Build one, test it against its acceptance criteria, sign it off, move on.

Before report 1 — verify the columns are populated

This audit read DDL, not data. Run this against one real lab database first. A column that exists but is null in 90% of rows changes the plan. 

-- Column presence + fill rate on the reporting-critical fields.
-- Run per lab. Anything under ~80% populated needs a decision before build.
SELECT
  COUNT_BIG(*)                                                    AS Tasks,
  SUM(CASE WHEN AssignedOn        IS NOT NULL THEN 1 ELSE 0 END) AS HasAssignedOn,
  SUM(CASE WHEN DateOpened        IS NOT NULL THEN 1 ELSE 0 END) AS HasDateOpened,
  SUM(CASE WHEN DueDate           IS NOT NULL THEN 1 ELSE 0 END) AS HasDueDate,
  SUM(CASE WHEN ActionCompleted   IS NOT NULL THEN 1 ELSE 0 END) AS HasActionCompleted,
  SUM(CASE WHEN DateCompleted     IS NOT NULL THEN 1 ELSE 0 END) AS HasDateCompleted,
  SUM(CASE WHEN ClosureReason     IS NOT NULL THEN 1 ELSE 0 END) AS HasClosureReason,
  SUM(CASE WHEN ExpectedResponseDate IS NOT NULL THEN 1 ELSE 0 END) AS HasExpectedResponse,
  COUNT(DISTINCT AssignedTo)                                  AS DistinctAssignees
FROM dbo.DenialTaskBoard WHERE LabId = @LabId;

-- Do all operational statuses map to a bucket? Anything listed here is unmapped.
SELECT Status, COUNT_BIG(*) AS Tasks
FROM dbo.DenialTaskBoard
WHERE LabId = @LabId
  AND ISNULL(Status,'') NOT IN
      ('New','Unassigned','Assigned','Payer Follow-up Required',
       'Pending Payer Response','Pending Documentation','Write-Off Pending Approval',
       'Escalated to AR Manager','Rework','Closed')
GROUP BY Status ORDER BY Tasks DESC;

-- Event coverage: are workflow changes actually producing history rows?
-- A task with status changes but no history rows means the audit trail has holes.
SELECT h.ActionType, COUNT_BIG(*) AS Events,
       MIN(h.ActionDate) AS Earliest, MAX(h.ActionDate) AS Latest,
       COUNT(DISTINCT h.ActionBy) AS DistinctActors
FROM dbo.DenialTaskHistory h
WHERE h.LabId = @LabId
GROUP BY h.ActionType ORDER BY Events DESC;

-- Follow-up schedule reality check: how many open tasks have a live follow-up date?
SELECT COUNT_BIG(*) AS OpenTasks,
       SUM(CASE WHEN n.NextFollowUpDate IS NOT NULL THEN 1 ELSE 0 END) AS WithFollowUp
FROM dbo.DenialTaskBoard t
OUTER APPLY (
    SELECT TOP 1 x.NextFollowUpDate
    FROM dbo.DenialClaimNotes x
    WHERE x.LabId = t.LabId AND x.ClaimId = t.ClaimID
      AND x.IsDeleted = 0 AND x.NextFollowUpDate IS NOT NULL
    ORDER BY x.CreatedOn DESC, x.NoteId DESC
) n
WHERE t.LabId = @LabId AND ISNULL(t.Status,'') <> 'Closed';
1RPT-03

AR Analyst Workload and Capacity

Build now

Start here. Pure current state, every measure comes from the latest task row, and it is verifiable against a screen we already ship — the totals must equal the AR Manager's Claim Assignment sidebar badges. That makes it the cheapest report to prove correct, and proving one report correct establishes the reconciliation pattern for the other eight.

Grain
One row per analyst, as of the selected date
Sources
DenialTaskBoard, DenialClaimNotes, DenialTaskHistory
Needs
GAP-2 (manager/team), GAP-1 (buckets), GAP-9 (aging)
Deferred
The Capacity column group

Have

  • Open claims, open denial lines, outstanding balance — direct from the task board
  • Work state split: unworked, active follow-up, pending payer, pending documentation, escalated
  • Unworked = no history or note row since AssignedOn
  • Average days since activity, oldest activity age — from MAX(ActionDate)
  • Mix by aging, classification, action, task, payer, priority

Missing

  • Manager and team — GAP-2
  • Configured capacity, workload units, utilisation, variance from team average — the whole Capacity group. The spec itself calls weighted workload an "optional MVP enhancement", so ship without it.
  • Overdue needs a ruling: DenialClaimNotes.NextFollowUpDate and DenialTaskBoard.ExpectedResponseDate are two competing due dates. Pick one as authoritative per status.

Test — RPT-03

  1. Pick one lab and one as-of date. Run the report for all analysts.
  2. Open Claim Assignment as an AR Manager on the same lab. Compare each analyst's open-claim count to the report.
  3. Drill into one analyst's Overdue count and confirm every row returned has a latest follow-up date before the as-of date and a non-closed status.
  4. Close one claim in the workflow app, re-run for the same as-of date, confirm it leaves the workload.
-- Acceptance: closed items excluded, and analyst totals reconcile to detail.
SELECT AssignedTo, COUNT(DISTINCT ClaimID) AS OpenClaims,
       COUNT(DISTINCT TaskID) AS OpenLines, SUM(InsuranceBalance) AS Balance
FROM dbo.DenialTaskBoard
WHERE LabId = @LabId
  AND ISNULL(Status,'') NOT IN ('Closed')
  AND NULLIF(LTRIM(RTRIM(ISNULL(AssignedTo,''))),'') IS NOT NULL
GROUP BY AssignedTo ORDER BY OpenClaims DESC;

Pass when — every analyst total equals its drill-down detail, closed items are absent, and changing a workload weight (if enabled) moves workload units without moving raw counts.

2RPT-01

AR Follow-up Activity Detail

Build now

The foundation report. Everything RPT-02 and RPT-05 measure is counted off this one's activity spine, so build it second and get the definition of a qualifying activity settled here rather than three times over.

The spine is a UNION ALL of DenialTaskHistory and DenialClaimNotes, with a synthetic activity id ('H:'+HistoryId / 'N:'+NoteId) because the two tables have independent identity sequences. Passive navigation creates no row in either, so the spec's exclusion of it is satisfied for free.

Grain
One row per qualifying activity event
Sources
DenialTaskHistory + DenialClaimNotes, joined to DenialTaskBoard and DenialLineItem
Needs
GAP-1, GAP-2, GAP-8 (source stamping)
Deliverable
A reusable vw_DenialActivityEvent

Have

  • Activity date/time, author, activity type, note text — both sources
  • Previous and new status, old and new assignee
  • Escalation events with reason, recipient and EscalationId
  • Accession, DOS and original charge by joining DenialLineItem on claim + CPT
  • Latest Activity Only — a ROW_NUMBER() over the spine

Missing

  • Contact method — not captured anywhere. Drop the column or add it to the note form.
  • Per-event balance snapshot — only the current balance exists. Either add it to the activity write, or label the column "current balance" and accept it is not a snapshot.
  • Update source and upload batch — GAP-8. Without it FR-012 fails.
  • Reporting status bucket — GAP-1
  • Follow-up category — GAP-5

Test — RPT-01

  1. On a test claim, as one analyst on one day: add three notes, change status once, raise one escalation.
  2. Run the report filtered to that claim and date.
  3. Assert 5 activity events and 1 distinct claim-day worked. This is the spec's own worked example and the single most important assertion in the suite.
  4. Toggle Latest Activity Only — expect exactly one row, the escalation.
  5. Export to Excel and confirm the summary counts equal the detail row count.
  6. Repeat the status change through the claim CSV upload instead of the UI, and confirm the two are distinguishable in the audit columns.

Pass when — repeated notes inflate the event count but not the claim-day count, and step 6 is distinguishable. If step 6 fails, GAP-8 is not done.

5RPT-02

AR Analyst Productivity Summary

Reduced scope

Reads directly off RPT-01's activity spine, so most of it is aggregation over work already done. Two things hold it back: opening and closing workload need GAP-6 snapshots, and the per-day denominator needs a working-day calendar.

Ship it without the workload reconciliation row rather than approximating opening workload from history. A reconstructed opening figure that is quietly wrong is worse than an absent one on a report used to assess people.

Grain
One row per analyst per period
Sources
RPT-01 spine + DenialTaskBoard + DenialClosedClaims
Needs
GAP-2, GAP-9 (calendar), GAP-6 for workload
Deferred
Opening/closing workload; appeal and rebill completion counts

Have

  • Claims worked, both daily distinct and period distinct — the spec's recommendation is to show both

Test — RPT-02

  1. Reuse the RPT-01 test claim. Confirm three same-day notes give a claims-worked of 1, not 3.

6RPT-05

Follow-up Due and Compliance

Reduced scope

This report has two halves and only one works. The current work queue — what is due, overdue, due today — is buildable now. The compliance half is not, because nothing records which activity satisfied which schedule, and the spec is explicit that an unrelated note must not count.

A useful accident of the design: because each note row carries its own NextFollowUpDate, the note table is already a schedule-instance history. Original due date, revised due date, revised by, revised on and reschedule count are all recoverable by ordering notes per task. What is missing is the category and the completion linkage.

Grain
One row per follow-up schedule instance
Sources
DenialClaimNotes, DenialClaimEscalations, DenialTaskBoard
Needs
GAP-5 for the compliance half
Deferred
Completed on time / late, compliance percentage

Have

  • Current overdue, due today, due soon and future from the latest open note per task
  • Original vs revised due date, revised by, revised on, reschedule count — by ordering notes
  • FollowUpReason as the reschedule reason
  • Current control group in full: status, days overdue, priority, recommended next action
  • Rescheduling already preserves history — a user cannot erase an overdue date, only add a newer note

Missing

  • Follow-up category — payer vs escalation vs documentation cannot be separated, and the spec requires them reported separately
  • Completion linkage — no way to say which activity satisfied which schedule, so on-time vs late is not computable
  • Cancelled schedules have no representation, so the compliance denominator is undefined
  • The Due Soon window is not configurable — GAP-9

Test — RPT-05

  1. Set a follow-up date in the past. Confirm the claim shows Overdue with the correct day count.
  2. Reschedule it into the future. Confirm the original date, the revision, the user, the timestamp and the reason are all still visible — the late history must not be erasable.
  3. Confirm reschedule count increments.
  4. Confirm current overdue counts use only latest open records and never every historical schedule row — this is the spec's stated implementation principle and the easiest thing to get wrong.
  5. Once GAP-5 lands: complete a payer follow-up with a documentation note and confirm it does not satisfy the schedule.

Pass when — steps 1–4 hold. Do not ship a compliance percentage until step 5 passes; a compliance figure computed from unlinked activity will be wrong and will be believed.

7RPT-07

Escalation Response and Rework

Reduced scope

The raised side is complete and well modelled — DenialClaimEscalations has level, reason, recipient, role, scope and a follow-up date. The response side does not exist as data. Average response time, the report's headline measure, is not computable safely.

It looks computable, which is the trap: a ManagerEscalationResponse history row does follow the escalation in time. But it carries TaskID, not EscalationId, so on any claim with more than one escalation cycle the pairing is a guess — and repeat escalation is precisely what this report exists to measure.

Grain
One row per escalation cycle
Sources
DenialClaimEscalations, DenialTaskHistory
Needs
GAP-4 for the Response and Rework groups
Deferred
Response time, rework turnaround, first-pass rate

Have

  • Escalations raised, by period, reason, level, recipient and role
  • Open escalations from the latest status
  • Days awaiting response and overdue flag, from NextFollowUpDate
  • Repeat escalation rate — distinct EscalationId per claim, which is exactly the spec's definition
  • Restricted internal escalation notes are already excluded from client-facing roles

Missing

  • Responded by, response date, response type, response note — no columns, no link
  • The whole Rework group — returned date, assigned analyst, completed date, cycle time
  • Escalation closed date and final resolution
  • Working-hours calendar for response time — GAP-9

Test — RPT-07

  1. Raise two escalations on the same claim, respond to the first only.
  2. Confirm the report shows two cycles, one open and one responded, and that repeat escalation rate counts the claim once.
  3. Confirm the responded cycle attributes the response to the first escalation, not the second. Before GAP-4 this test will fail — that failure is the argument for GAP-4, so run it and record the result.
  4. Confirm a response does not close the claim or the escalation.
  5. Confirm a manager response returns the claim to the same assigned analyst unless a reassignment event exists.

Pass when — steps 1, 2, 4 and 5 hold. Step 3 is the acceptance gate for GAP-4 and is expected to fail on the reduced version.

8RPT-04

Action Completion

Blocked — GAP-3

Do not attempt this before GAP-3. The report's entire premise is that the moment a user marks an action complete becomes that action's business date — the Appeal Date, the Rebill Date, the Write-off Completion Date. We do not store that moment.

DenialTaskBoard.ActionCompleted is a bit and DateCompleted is a date with no time, no actor, and no protection from being overwritten by the next status change. The spec additionally requires the completion event be immutable, with corrections recorded as audited amendments. Every one of those properties is absent.

A partial version built on the current flag would produce Appeal Dates that silently change and average-days-to-completion figures that drift as claims are re-worked. That is worse than no report.

Grain
One row per completed action or task event
Blocked by
GAP-3 — DenialActionCompletion
Also needs
GAP-8 (source), GAP-2 (manager)
Unblocks
RPT-02 completion measures, RPT-09 stop events

Test — RPT-04, once GAP-3 exists

  1. Complete an appeal. Confirm the report shows it with the label Appeal Date; complete a rebill and confirm Rebill Date; a write-off and Write-off Completion Date. Same stored field, three labels.
  2. Confirm completed by and a full timestamp are recorded, not just a date.
  3. Change the claim's status afterwards. Confirm the completion timestamp does not move.
  4. Correct a completion. Confirm an audited amendment appears and the original survives.
  5. Complete an action via Excel upload. Confirm it validates identically to a UI update and is separately identifiable.
  6. Confirm the completed-action count equals the number of rows carrying a completion timestamp.

Pass when — step 3 holds. If a later status change moves the completion timestamp, GAP-3 has been implemented as another mutable column and the report is still not trustworthy.

9RPT-09

Operational SLA

Blocked — GAP-7

Last, and dependent on almost everything before it. We have exactly one SLA: an integer SLADays on the task with a derived DueDate, DaysRemaining and SLAStatus. The spec asks for six configurable SLA types, each with its own start event, stop event, calendar, target, warning threshold and applicable dimensions, versioned so historical results stay reproducible.

The dependency chain is the real point: appeal completion and rebill completion SLAs cannot stop their clocks until GAP-3 exists, and escalation response SLA cannot stop until GAP-4 exists. Four of the six initial SLA types are blocked behind other gaps, not behind GAP-7 itself. Sequencing it last is not caution, it is arithmetic.

Grain
One row per SLA measurement instance
Blocked by
GAP-7, and GAP-3 + GAP-4 for four of six SLA types
Also needs
GAP-9 (calendar), GAP-2 (manager)
Available today
The existing task due-date SLA, reportable as one type

Test — RPT-09, once GAP-7 exists

  1. Configure a first-follow-up SLA with a 3-day target and a 1-day warning. Create a claim; confirm an instance is created with explicit start event, due time and threshold.
  2. Let it pass the warning threshold. Confirm it reports as Near Breach, not yet Breached.
  3. Let it pass the target. Confirm it reports as an active breach, and that active and completed breaches are counted separately.
  4. Complete it. Confirm the result traces to explicit start and end events, not to a computed status.
  5. Change the target with a new effective date. Confirm historical instances keep their original result and only new instances use the new target.
  6. Move an item to a configured pause status. Confirm elapsed, pause and net duration are reported separately and the pause history is preserved.
  7. Confirm in-progress instances are excluded from the met-percentage denominator but shown separately.

Pass when — step 5 holds. A target change that rewrites historical SLA results makes every prior month's reporting unreproducible, which is the failure mode this report exists to avoid.

Section 05

Recommended sequencing

Two schema passes, three delivery waves.

  1. Schema pass A — do this first, before any report. GAP-1 status bucket map, GAP-2 manager/team dimension, GAP-8 source stamping, GAP-9 calendar and aging buckets. All additive, none touches a write path except GAP-8, and between them they touch every report in the suite. Start the GAP-6 snapshot job in this pass too, even though nothing reads it yet — it only accrues value from the day it starts running.
  2. Wave 1 — RPT-03, RPT-01, RPT-08. Three complete reports and the reusable activity view. This proves the reporting architecture end to end: filters, as-of context, grain labels, drill-down, Excel export with reconciliation totals, and role-based masking. Get FR-001 through FR-012 right once, here, and the remaining six inherit them.
  3. Wave 2 — RPT-06, RPT-02, RPT-05, RPT-07, each at reduced scope with the deferred measures visibly marked Not Available and their missing dependency named, as FR-011 requires. Do not hide a deferred measure; a named gap is a feature request, a hidden one is a surprise in UAT.
  4. Schema pass B. GAP-3 action completion events, GAP-4 escalation response and rework, GAP-5 follow-up category and completion linkage. These change write paths in SqlDenialWorkflowRepository and need their own regression pass against the existing workflow screens.
  5. Wave 3 — RPT-04, then the upgraded RPT-02, RPT-05 and RPT-07, then GAP-7 and RPT-09 last. By this point RPT-09 has real start and stop events to measure between, which is the only way it will produce numbers anyone should act on.
One thing to settle before Wave 1. There are two competing due dates in the system: DenialClaimNotes.NextFollowUpDate, set by the analyst, and DenialTaskBoard.ExpectedResponseDate, required when a claim moves to Pending Payer Response or Pending Documentation. RPT-03, RPT-05 and RPT-06 all report "overdue" and will disagree with each other unless one rule decides which field governs for which status. This is a product decision, not a development one, and it needs an answer before the first overdue figure is shown to a client.

Open questions carried from the spec

The specification's §7 lists seven configuration decisions. Three of them block Wave 1 and should be answered now rather than at build time:

  • Working-day calendars by client and team — blocks RPT-02's per-day denominator.
  • Which statuses require a next follow-up date, and the Due Soon window — blocks the overdue definition above.
  • Client-facing note categories to mask or exclude — blocks RPT-01's restricted view, and it is a disclosure question, so it needs answering before anything ships to a client role rather than after.

The other four — productivity display grain, workload weights, SLA pause statuses, and accepted financial outcome evidence — can wait for the waves that consume them.
